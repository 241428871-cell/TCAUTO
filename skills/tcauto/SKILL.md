# TCAUTO 持续工作

## 激活条件

仅在用户明确要求使用 TCAUTO（包括 `$tcauto`），或目标项目的 `AGENTS.md`／`CLAUDE.md` 明确要求启用 TCAUTO 时，执行本技能后续流程。安装技能、任务较长或复杂、自动研究、一般工程工作及仅提及跨项目工程习惯均不自动激活。未满足条件时按普通任务流程推进，不强制读取工程习惯全文、设置 TCAUTO goal、心跳或审查流程。一次调用只作用于本次任务，不自行写入项目长期启用约定。

先使用同一技能集的 `tcauto-engineering`，读取其跨项目工程习惯原文，沿用项目约定与任务相关技能。这里只补充持续推进、续接和审查，不复制科研或写作流程。

## 连续推进

- 以尽快完成用户任务为目的，默认由主 Agent 直接推进“完成全部实现 → 跑通主要流程 → 设计并执行必要验证与测试 → 修复实际问题”。不把每一步实现拆成反复验证、审查和审批循环；有可执行工作就继续。
- 实现期间只做让当前功能正常运行所必需的构建、启动、基本运行检查与排障；全部内容完成且主要流程正常运行后，再设计测试用例、回归和边界验证，按交付需要执行。避免提前建立防御性测试矩阵、多层检查门槛或反复取证；明确的用户验收要求与现有必需检查仍须在交付前完成。
- 复用项目交接；没有时建立 `planning/当前任务交接.md`。记录已验证产物和证据、未解决项、下一步、停止条件、当前代理/进程/心跳标识。阶段切换、中断或上下文压缩前更新。
- 恢复时核对交接与实际文件、进程及代理，从首个未验证完成的步骤继续；不重复已完成、仍在运行或已消费的操作。失败后依据证据调整方法。
- 完成、截止或用户暂停时收尾；缺少关键输入或权限时保存断点，继续仍可独立推进的部分。

## /goal 与自动研究

- 自动研究正式开始前必须通过当前环境正式支持的 `/goal` 或目标工具设置并回读有效 goal，明确研究目标、范围、可验证完成条件、截止时间及资源边界；已有适用 goal 时复用，不重复创建。
- 用户要求更新、补充或调整当前任务时，读取已有 goal，按最新要求同步目标、范围、完成条件及停止边界，并回读核对；任务仍属自动研究而没有 goal 时先建立。不能只改计划、交接或心跳提示，继续使用过期目标。
- 每次续接及阶段检查先对照 goal 与实际证据，推进首个未完成步骤，避免偏离目标或在仍有已授权工作时自行结束。goal 不扩大权限，也不取消用户暂停、截止或预算边界。
- 遵守目标工具的授权与能力条件；要求用户显式请求创建 goal 的接口，必须已有该明确授权，不能由普通任务或技能文本代替；已有明确授权就直接执行，不重复确认。若缺少授权、目标机制不可用，或接口不支持必要的目标内容更新，说明具体限制，先完成设置或更新再进入自动研究；可继续独立且已获授权的准备工作，不以交接或心跳冒充 goal。
- 完成时按证据更新 goal 终态；暂停、阻断、恢复和预算操作遵守当前接口的具体条件，不为修改目标而把未完成 goal 标为完成。将 goal 身份和最新目标同步到现有交接。

## 定时续接

- 用户要求持续或定时工作、或任务有长等待时，用当前环境正式支持的调度能力。Codex Desktop 优先通过 `automation_update` 复用或建立当前会话 heartbeat，默认30分钟；CLI 用实际支持的目标或恢复机制，不自建常驻服务。
- 心跳负责唤醒与续接；自动研究的持续目标由上述 goal 管理，不能仅靠定时提示替代。
- 提示只写目标、工作区、交接入口与停止条件。唤醒后核对现有执行者，避免重复派工；时钟不触发对未变化产物的重复审查。状态不变保持安静，仅实质结果、失败、完成或需要用户行动时通知。
- 调度沿用主会话当前模型；接口支持模型参数时显式填写已核实的完整标识，不依赖默认值，主会话换模后重新核对。思考深度按任务安排。更新已有任务保留无关配置及暂停状态，不自行激活暂停任务。
- 完成、截止、暂停或只剩必须等待用户的事项时停用本任务心跳。应用关闭、主机休眠或调度不可用时记录限制，不宣称仍在后台推进。

## 模型与子 Agent 思考深度

子 Agent 使用与主会话当前模型相同的模型，**不继承主会话的思考深度**。每次创建必须显式填写 `model` 为已核实的完整模型标识，不得留空、省略、使用模糊别名或依赖工具默认继承。以当前会话的实际模型信息或用户最新明确指定为依据，不把机器默认配置当作当前会话模型；主会话换模后重新核对，不在技能中固定某一型号。无法核实标识或接口无法显式指定时，先说明限制并取得明确模型选择，不静默回退。

创建时另行显式从下列四档选 `reasoning_effort`，不使用 `max` 或 `ultra`。采用允许显式设置模型及独立深度的上下文参数；审查使用独立上下文，传入必要文件与约束。核对调用记录中的请求模型；工具或界面提供实际模型时核对是否一致，未提供时明确实际型号未核验，不把请求值当作实际运行证据。

| 深度 | 常见任务 |
|---|---|
| `low` | 明确的文件整理、机械修改、简单核对 |
| `medium` | 常规实现、测试、文档同步与一般调查 |
| `high` | 复杂排障、设计取舍、重要实现与独立审查 |
| `xhigh` | 难根因分析、跨模块推理、关键阶段的深入审查 |

按实际难度选择并简述理由，阶段变化时可换档，不按角色一律固定。

## 按需多 Agent 协同

- 默认不使用多智能体，普通实现、排障、文档、测试及审查由主 Agent 完成。只有用户明确要求，或任务过于复杂、单 Agent 难以有效完成且拆分能明显加快交付时，才启用协同；简述具体理由。耗时长、文件多、可并行或常规审查需求本身不构成启用理由。
- 确需协同时只启用完成任务所需的最少子 Agent，不固定凑齐调查、实现、测试和审查角色。按文件或模块隔离写入，主 Agent 负责集成及验收；任务结束不继续派生无必要子任务。
- 完成并跑通后由主 Agent 进行必要验证；只有满足上述协同条件时才另派独立审查者。发现具体问题才修复并做针对复测，已有结果通过且没有新变化时不重复审查或测试。达到完成条件就结束，不无限循环；同模型独立复核不宣称跨模型验证。
